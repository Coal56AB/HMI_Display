# Подключение интерфейса без изменения платформы

`Firmware/Api/display_api.h` принадлежит общей платформе. Текущая версия API — 2.
В `templates` и `PCH_HMI` используются одинаковые исходники `Firmware`.
Реализация интерфейса не включает `board.h`, `main.h` или заголовки HAL.

Очередь обновлений, сравнение пикселей и порядок отрисовки предоставляет
`Firmware/Api/display_renderer.h`. Интерфейс рисует содержимое через канву
и задаёт настройки обхода: [API отрисовки и примеры](RENDERER.md).

## Точки входа

- `display_init(const DisplayPlatform *)` — один раз после подготовки ресурсов.
- `display_event(const DisplayEvent *)` — касание, байт UART или ошибка UART.
- `display_step(uint32_t now_ms)` — обработка накопленных данных, таймеров и отрисовка.

Отдельный tick не нужен. Обновление времени — аргумент step, монотонные миллисекунды
с переполнением uint32_t. Разности времени вычисляйте беззнаковым вычитанием.

UART-события могут приходить из прерывания: только помещать данные в очередь,
не рисовать, не обращаться к SPI и не выполнять блокирующих операций.
Касания опрашиваются между передачами LCD, затем передаются модулю вне отрисовки.
Буфер касается только доставки событий; смысл жестов определяет модуль.

## Сервисы платформы

[Точки расширения ESP32](ESP32_PLATFORM.md) описывают подключение сервисов приложения
и его таблицы разделов. Чистая ESP32-платформа предоставляет только дисплей, сенсор,
время и перезапуск.

`DisplayPlatform` содержит геометрию экрана, вывод прямоугольника RGB565,
чтение ресурсов, чтение/запись/стирание Flash, текущее время, отправку UART,
сброс и сообщения прогресса запуска. Буфер write_rect можно переиспользовать
после возврата: передача синхронная. Координаты и stride задаются в пикселях.

Flash API принимает абсолютные адреса W25Q16 (2 МБ); область ресурсов от нуля
до округлённого вверх размера образа защищена от записи/стирания через этот API.
Стирание — выровненный сектор 4096 байт. Раскладкой настроек и журнала управляет модуль.
Плата и драйвер задают реальные аппаратные возможности; новый MCU требует своего
аппаратного проекта с реализацией этого же API.

## Ресурсы и запуск

Помимо трёх функций модуль предоставляет константу `display_module`:
версию API, длину ресурсов, необязательные callbacks проверки образа, ошибки и
счётчика чтений. Проверка вызывается до init и после записи ресурсов; формат
заголовка и CRC знает только модуль. При отсутствии ресурсов длина равна нулю,
callbacks могут быть NULL. Внутренний шрифт и буфер терминалки принадлежат платформе.

`Firmware/Api/display_empty.c` — пустая реализация. При подключении интерфейса
исключите её из сборки и добавьте свои исходники, include-пути и defines.
Ни один C-файл платформы править не требуется.

## Сборка и подключение

`BUILD.cmd --display-dir D:\MyDisplay` создаёт временный проект в `.build/Keil`.
Исходный `.uvprojx` и C-файлы остаются неизменными. Без `DisplaySrc/module.json`
собирается пустая реализация из `Firmware/Api`.

Манифест модуля содержит `apiVersion: 2`, `name` и `firmware` со списками
`sources`, `includes`, `defines`. Пути относительны каталогу модуля.
`assets`, `resourceBuild` и `simulator` нужны только использующим их модулям.

Конкретный модуль может поставлять `CONNECT.cmd`: окно на PySide2 выбирает
`.uvprojx` и target, проверяет API, затем заменяет группу DisplaySrc, include-пути
и defines. До записи создаётся `.uvprojx.bak`. Файл `.display.json` хранит выбранные
пути для корректной повторной замены интерфейса. Оба файла локальные, не входят в Git.
Такое подключение намеренно меняет состав проекта Keil, но не его C-код.

## Проверка границы

`Scripts/Check/check_platform_boundary.py` собирает альтернативный модуль и
проверяет побайтовую неизменность исходников и проекта платформы.
Общие изменения сначала коммитятся в templates, затем вливаются в ветки интерфейсов.
